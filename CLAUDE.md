# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A ZMK firmware configuration for a MoErgo Glove80 split keyboard. There is no
application code here — the deliverable is `config/glove80.keymap` (and
`config/glove80.conf`), which get compiled into `glove80.uf2` firmware by the
upstream `moergo-sc/zmk` build (via Nix), either locally in Docker or via
GitHub Actions.

## Files

- `config/glove80.keymap` — the actual keymap: layers, behaviors, macros,
  combos. This is the file to edit for any keybinding change. It was
  originally generated by the Glove80 Layout Editor webapp but is now hand
  edited directly.
- `config/glove80.conf` — Kconfig options passed to the ZMK build. Currently
  empty.
- `config/info.json` — physical key layout/geometry (`row`/`col`/`x`/`y`/`r`
  per key position, labeled `L_C<col>R<row>` / `R_C<col>R<row>` / `L_T*`/`R_T*`
  for thumb keys). Reference this when a commit message needs physical key
  coordinates.
- `config/default.nix` — Nix build definition; builds left (`glove80_lh`) and
  right (`glove80_rh`) halves separately using `glove80.keymap` +
  `glove80.conf`, then combines them into one `.uf2`.
- `config/keymap.json` — a Glove80-Layout-Editor export. **Note: it is stale**
  (still shows the original default `base`/`fn` layers) and is not consumed
  by the Nix build at all — `glove80.keymap` is the sole source of truth for
  firmware builds. Don't assume the two are in sync.
- `.github/workflows/build.yml` — CI: checks out this repo plus
  `moergo-sc/zmk` (main), runs `nix-build config -o combined`, uploads
  `glove80.uf2` as a build artifact.
- `Dockerfile` / `build.sh` / `build.bat` — local equivalent of the CI build.

## Build

Local build via Docker (pulls/builds a Nix environment with the ZMK
toolchain, so the first run is slow):

```sh
./build.sh [branch]      # branch defaults to "main" (moergo-sc/zmk branch/tag)
```

```bat
build.bat [branch]
```

This produces `glove80.uf2` in the repo root. There is no separate lint/test
command — the Nix build itself is the correctness check (it will fail on
keymap syntax errors, undefined behaviors, invalid Devicetree, etc.).

To build for a specific `moergo-sc/zmk` branch or tag (e.g. to test against a
firmware release), pass it as the argument to `build.sh`/`build.bat`.

Pushing to GitHub runs the same build via `.github/workflows/build.yml`;
firmware is downloaded from the run's "Artifacts" section.

## Keymap architecture (`config/glove80.keymap`)

- **Layers** are defined via `#define LAYER_<name> <index>` near the top of
  the file, and correspond 1:1 to `layer_<name> { bindings = < ... >; };`
  blocks inside the `keymap { }` node. Current layers: `unix` (0), `windows`
  (1), `symbol` (2), `magic` (3), `basic` (4). Layer switches in bindings use
  `&to LAYER_<name>` / `&mo LAYER_<name>` / `&MO_KP LAYER_<name> <key>`, so
  renaming a layer means updating both the `#define` and the `layer_<name>`
  node name, plus every reference — do this with the `layer_<name>` /
  `LAYER_<name>` naming pair kept in sync (word-boundary-safe rename, since
  e.g. `LAYER_base` is a substring-prefix of `LAYER_base_win`).
- **Home row mods** are custom behaviors named `HRM_left_pinky`,
  `HRM_left_ring`, `HRM_left_middle`, `HRM_left_index`, `HRM_right_index`,
  `HRM_right_middle`, `HRM_right_ring`, `HRM_right_pinky`, used as
  `&HRM_<hand>_<finger> <mod> <key>` on the home row of the base layers.
- **Macros** (in `macros { }`) implement OS-aware app-switching/clipboard
  shortcuts: `copy`/`paste`/`screenshot`/`move_most_recent_app` for one OS
  and `_win`-suffixed twins (`copy_win`, `paste_win`, `screenshot_win`,
  `move_most_recent_app_win`) for the other, bound on the `unix`/`windows`
  layers respectively.
- **`magic` layer / `&magic` behavior**: a hold-tap style behavior
  (`magic LAYER_magic 0` in bindings) used as a corner key on multiple layers
  to momentarily access the magic layer (BT management, RGB, mouse emulation).
- **Combos** are defined in `combos { }` (e.g. `combo_underscore`).
- Physical key references in comments/commit messages follow `LH`/`RH` +
  `C<col>R<row>` (matching the `label`s in `config/info.json`), or `T1`-`T6`
  for thumb keys.

## Commit conventions

Commits that touch keymap/config files use a project-specific changelog-style
message format (`YYMMDD - vX.Y` header + `type(scope): description` bullets)
instead of a normal single-line subject — see the `keymap-commit` skill
(`.claude/skills/keymap-commit/SKILL.md`) for the exact format, version
derivation, and scope/type conventions. Use that skill when committing
keymap changes; unrelated commits (tooling, docs) use normal commit messages.
